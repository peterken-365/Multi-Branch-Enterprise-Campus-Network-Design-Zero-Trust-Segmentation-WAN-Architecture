Automation & Cloud Readiness

Configuration as code, drift detection, an API-ready management plane, and ring-fenced address space for the Azure hybrid extension — the operational layer that keeps this design maintainable after day one.

Pillar 4 · Part 1

Configuration as source-of-truth

Manual CLI typing does not scale and does not detect unauthorized change. The six golden .cfg files in 02-switching-and-routing-design/configs/ are the authoritative definition of the network — version-controlled in Git, where every change is a reviewed commit.

Nightly backup & drift workflow

  1. Pull running-config over SSH — scripts/backup-and-drift-check.sh (cron 30 23 * * *) or the Ansible playbook.
  2. Store timestamped copy — backups/<device>-<date>.cfg on the backup host (server farm in production).
  3. Diff vs golden config — the script exits non-zero on drift and prints the differences.
  4. Review & reconcile — drift is an unauthorized change until proven otherwise; update the golden file via a Git PR.
drift detection logic
golden config (Git)                        <----  expected state
        | diff
running-config (device, via SSH/Ansible)   <----  actual state
        |
        +--> [OK]    no drift        --> retain backup, no action
        +--> [DRIFT] differences    --> page netops; unauthorized-change process
Zero dependencies by design: the shipped bash script uses plain ssh + diff with SSH key auth to each device's management IP as netadmin. The Ansible playbook is the production upgrade path (cisco.ios collection, network_cli connection).

Cloud extension readiness — Azure S2S VPN

The IP plan and the R1 edge design already ring-fence everything the Azure hybrid extension needs, so the capstone requires zero re-addressing.

ResourceBlock / ValuePurpose
Azure-mapped address space10.20.200.0/24Reserved for Azure VNet subnets peering into HQ — never allocated on-prem
Tunnel transit10.20.254.8/30R1 Tunnel0 = 10.20.254.9 — point-to-point transit inside the IPsec tunnel
BGP peeringeBGP ASN 65001 ↔ 65515R1 ↔ Azure VPN Gateway via 169.254.21.0/30 inside the tunnel
S2S VPN design overview (Project 5)
Nairobi HQ (R1-HQ-EDGE) ============== IPsec/IKEv2 S2S ============ Azure VPN Gateway
  Tunnel0: 10.20.254.9/30                                  10.20.254.10/30 (Azure side)
  eBGP: 169.254.21.2 (ASN 65001)                           169.254.21.1 (ASN 65515)
  Advertises: 10.20.0.0/16 (summary)                       Advertises: 10.20.200.0/24
  1. Address-space discipline: reserving 10.20.200.0/24 today prevents an accidental DHCP expansion from colliding with Azure tomorrow — the #1 rework cause in hybrid migrations.
  2. Edge discipline: EDGE-INBOUND and NAT-PERMITTED were written so that adding one tunnel interface + IKEv2 profile does not require touching the zero-trust ACL matrix.
  3. Skills path: demonstrates understanding that cloud integration is a routing + identity + IPsec problem, not a UI wizard.
Template ready: the IKEv2 proposal/policy/keyring/profile, Tunnel0 and the BGP block are pre-written in azure-vpn-tunnel-template.cfg — commented, NOT applied, and applied only during Project 5 alongside the Azure VPN Gateway deployment.
